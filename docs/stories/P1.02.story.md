# P1.02 — Snapshot de contexto e identidade de LLM

- epic_id: P1
- status: in-review
- fonte: `docs/architecture/prd.md`
- arquitetura: `docs/architecture/architecture.md`
- dependência: `docs/stories/P1.01.story.md`

## Problema

O repositório descreve snapshots, mas não possui contrato, localização ou regra operacional. Duas LLMs podem ler revisões diferentes, usar autonomias incompatíveis ou transportar dados distintos e ainda declarar que compartilham o mesmo contexto.

## Resultado

Garantir que humanos e LLMs identifiquem exatamente qual contexto, autoridade e dados utilizaram.

## Escopo

- manifesto portável de contexto por commit;
- versões do charter, decisões e contratos consumidos;
- provedor, modelo/versão disponível, autonomia e origem do contexto;
- dados permitidos e proibidos;
- validade e regra de invalidação seletiva.

## Decisões de implementação

- Cada tarefa com LLM referencia `contexts/<task-id>.context.json`.
- `docs/context-manifest.schema.json` é o contrato portável e não exige campo específico de fornecedor.
- `docs/context-registry.md` define criação, verificação, invalidação e reentrada.
- O snapshot guarda referências e revisões, nunca conteúdo integral de conversa, prompt, segredo ou dado pessoal.
- Mudança invalida somente manifestos que observam a referência e a classe alteradas; mudança editorial registrada não invalida contexto material.
- Manifesto ausente ou inválido permanece legível, mas sua autonomia efetiva é `read-only`.

## Tarefas

1. Criar o contrato JSON Schema para humano e LLM.
2. Definir o registro canônico em `contexts/` e o algoritmo seletivo de invalidação.
3. Vincular snapshot, roteamento e consumidor ao template de tarefa.
4. Exigir identidade/autonomia/dados antes de execução por LLM.
5. Validar interpretação equivalente, validade temporal/eventual e mudanças relevantes/irrelevantes.

## Acceptance Criteria

- AC-P1.02-01: 100% das tarefas de LLM referenciam um snapshot.
- AC-P1.02-02: snapshot identifica commit e documentos canônicos lidos.
- AC-P1.02-03: mudança relevante invalida apenas consumidores afetados.
- AC-P1.02-04: dados e autonomia ausentes bloqueiam execução, não leitura.
- AC-P1.02-05: dois fornecedores distintos conseguem interpretar o mesmo manifesto sem campos proprietários obrigatórios.

## Validação

Reproduzir uma tarefa em duas LLMs e verificar se ambas listam os mesmos limites, versões e próximo consumidor.

Também validar:

- manifesto LLM completo aceito;
- ausência de identidade, autonomia ou dados rebaixa a leitura para `read-only` e bloqueia execução;
- mudança de contrato invalida somente snapshots que observam esse contrato;
- mudança não observada e correção editorial registrada preservam os demais snapshots;
- todos os commits referenciados resolvem como commits Git quando disponíveis no clone.

## Segurança e limites

- Não armazenar prompt integral, transcrição privada, segredo, token ou dado pessoal no manifesto.
- Identidade de modelo é alegação operacional, não prova de independência ou qualidade.
- Snapshot válido não autoriza mudança de alvo, risco, dados ou ação irreversível.

## Evidência de implementação

- contrato validado como JSON Schema Draft 2020-12;
- manifestos completos de consumidor humano e de dois fornecedores LLM aceitos;
- nove casos inválidos bloquearam identidade, autonomia, dados, autorização, versão exposta ausente, dado proibido e extensão proprietária;
- os dois fornecedores produziram a mesma visão de revisões, limites e próximo consumidor;
- mudança de contrato invalidou somente o consumidor observador; mudança não observada e editorial preservaram os demais;
- a revisão do projeto resolveu como commit Git.
- o comando genérico `npm --prefix packages/server test -- yolo` foi executado e classificado `[N/A]`: este repositório documental non-UI não possui `packages/server` nem runtime npm. As validações do schema e dos contratos substituem a seleção incompatível; o harness portável permanente continua em P1.04.
